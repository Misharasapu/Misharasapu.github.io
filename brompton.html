Brompton: tyre wear classification

A computer vision prototype that sorts a photo of a Brompton tyre into Good, Monitor or Replace, which I built over a 10-week internship by first growing the dataset and then rebuilding the evaluation around the tyres that actually need replacing.

Context
AI/ML engineering internship, Brompton Bicycle, London

Problem

Tyre wear is usually judged by eye, which is inconsistent and hard to scale, and a worn tyre is a safety problem rather than just a maintenance one. The aim was a prototype where a rider uploads a photo of their tyre and gets a clear Good, Monitor or Replace result, with advice on what to do next.

Approach

I scoped the work to tyres only, because tyre wear is visible in a photo, it matters for safety, and of the parts in the original data (front and rear tyres, chains and brake pads) tyres gave the clearest signal.

The first model was built on the original dataset, where unsafe tyres were rare. So before more modelling I collected more photos from staff bikes, the workshop and recycled tyres, aiming at unsafe tyres in particular, which expanded the dataset by roughly two and a half times, and I kept every photo of the same physical tyre in the same split so the model could never be tested on a tyre it had already seen.

A second model identifies the tyre type, so whether it is a Slick, a Commuter Lite or a Commuter Heavy, which lets the advice suggest a suitable tyre rather than a generic one. Before any prediction is shown, an image quality gate checks resolution, blur and brightness, and a low-confidence result is designed to ask the rider to retake the photo, although that check was switched off during user testing.

Key decision: stop trusting accuracy

The first run looked strong on headline accuracy, but on limited data it missed too many unsafe tyres. Most tyres in the data were in good condition, so a high accuracy said little about the rare unsafe ones. So I expanded the data and made Replace recall the main metric, which means out of all the tyres that really needed replacing, how many the model caught, and every later choice of data, model and threshold was judged on that first.

Results

Recall on unsafe tyres rose sharply once the new data was in, which made the data collection the most useful decision of the project. I ended up keeping two models on purpose: a safety-first model tuned to catch as many unsafe tyres as possible, kept as the internal reference, and a calmer model for user testing, because the safety-first one flagged so many tyres that it was not usable in a demo.

The prototype runs as a Streamlit app that takes the rider's riding priority, weekly mileage and rain exposure and turns the two model outputs into personalised advice, such as when to check the tyre again or which tyre type to switch to.

Limitations and next steps

  • The model in the demo app is the user-testing one, so it is a prototype for feedback and not a production safety tool, and the low-confidence retake was switched off during user testing.
  • Labels follow mechanic judgement, and workshop tyres are often replaced for cuts or sidewall damage rather than tread wear, so the model is learning a mechanic's call and not a measured tread depth.
  • Only tyres have a model. Brake pads and chains were explored for feasibility but have no committed model yet.
  • The next test would be a fresh set of rider photos that played no part in development.
